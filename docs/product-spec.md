# TaskPulse —— 需求与实现规格（交接给开发团队）

> 本文是「一个东西大概长什么样、为什么这么设计」的完整说明，不是逐行实现说明。
> 目标：换一个团队用自己熟悉的技术栈，能做出 80% 等价的成品。
> 平台基线：macOS（Apple Silicon / Intel 均可）。Windows 版本见文末「跨平台评估」。

---

## 1. 产品一句话

一个常驻在屏幕边缘的**极窄悬浮条**，实时显示我在 Agent 平台上所有会话的状态（进行中 / 待我处理 / 卡住），
需要时悬停展开看列表，单击某个任务直接跳到对应的浏览器标签页。

它不是监控大盘，是「眼角余光」——**最小化占用、最大信息密度、零点击成本**。

---

## 2. 用户与使用场景

- 用户同时跑 5~15 个 Agent 会话，标签页常年 100+，分组管理。
- 主要问题：不知道哪个会话已经跑完等我、哪个卡住了；切标签的成本高。
- 核心场景：
  1. 余光扫一眼窄条上的三个数字，判断「要不要管」。
  2. 悬停展开，看清哪一组、哪个任务需要处理。
  3. 单击任务 → 浏览器直接切到那个标签页。
  4. 处理完，要么点勾选框（彻底结束），要么切到标签页（自动标记已查看）。
- **不允许**的体验：遮挡内容、抢焦点、拖到边缘位置乱跳、每次点击后弹一堆窗口。

## 3. 硬性交互要求（来自产品负责人的原话，逐条都是验收点）

1. **收起态只有 44pt 宽**，垂直三个数字胶囊（进行中/待我处理/卡住），颜色区分、0 时暗显。
2. **悬停自动展开成 240pt 卡片**，鼠标离开 0.15s 后自动收起。不允许「松手后自己弹开」。
3. **拖到屏幕任意边缘立即收缩**（同一帧内完成），且停在松手的高度；不自己挪到屏幕中间。
4. **双击标题栏**切换展开/收起；**单击任务行**跳转标签页（一次点击即切走，不做二次确认）。
5. **图钉**：固定常展开，重启后保持。
6. 计数胶囊**可点击筛选**：点「卡住」进入筛选视图；再点一次恢复全部。
   数字为 0 的胶囊也**必须可点**。
   - 筛选时**所有组都要留在列表里**（组头一行，不因为没命中就整组消失），
     这样一眼能看出当前状态分布在哪些组；
   - 没有命中会话的组保持折叠、组头与右侧数字压暗；命中的组自动展开，
     **只漏出处于该状态的会话**并带该状态的颜色，组头改成「命中数/总数 个会话」；
   - 没有组（未分组）的会话单独占一行，未命中的保持已查看的暗色；
   - 手动点开的组仍然显示它的全部会话（未命中的暗色）。
7. **已查看（seen）的任务不消失**：它以暗蓝色留在列表里、不计入任何数字，
   直到用户勾选对勾或在浏览器关掉对应标签页才彻底消失。
8. Agent 回话、任务疑似卡住/限流/超时时，屏幕右上角弹**提示条**（同一个组件）：
   事件由后端放进 `/state` 的 `events`，App 自己弹，**不走系统通知**——`osascript` 发的通知
   会被 macOS 记在「脚本编辑器」名下，点它只会打开编辑器；
   - 停留 15 秒自动消失；
   - 多条同时到达时**向下堆叠**，叠压 20pt，**保证每条的标题和正文完整可见**；
   - **点一下立刻跳到对应标签页**（目标延迟 ≤60ms），点击时要有「点到了」的即时反馈动效。
9. 跳转的取舍，按「有这个会话的标签页吗」分两种，没有第三种：
   - **有** → 聚焦它（`chrome.tabs.update` + 窗口置前），不新开；
   - **没有** → 新开一个标签打开该会话；
   - **不会**把某个已开的 DataAgent 页面「导航」到目标会话。那样虽然省一个标签，
     却会把用户正看着的会话换掉——行为不可预期，用户会分不清是自己切走了还是程序改的。
   扩展会把实际动作随 ack 回传（`focused` / `created` / `expired`），日志里能区分。
10. 全程**不抢焦点**（面板是非激活面板），不出现 Dock 图标。

## 5. 数据与状态机（核心）

### 5.1 五个状态

| 状态 | 含义 | 计数 | 展示 |
|---|---|---|---|
| `running` | Agent 正在跑 | ✓ | 亮蓝 |
| `stuck` | 这一阶段超过阈值（默认 1800s = 30 分钟）或**限流失败**（见 5.3） | ✓ | 亮红 |
| `attention` | Agent 停下且**有新回复**未查看 | ✓ | 亮橙 |
| `seen` | 用户看过了（切过标签页/点过行），但会话还开着 | ✗ | **暗蓝**；48h 无新进展自动归档 |
| `done` | 用户勾选确认，或历史数据 | ✗ | 隐藏（仅在「显示全部」里出现） |

关键点：`seen` **仍属于它原来的状态**（字段 `prev` = running/attention/stuck）。
但计数的口径是「此刻真实状态」：点「进行中」只列真正的 running 行，与数字严格一致；
已读的暗色行只在无筛选视图 /「全部」里出现（它表示「看过但已停下」，不是在干活）。

### 5.2 状态迁移规则

```
定期对最近 20 个会话采样，间隔内优先复查仍在运行的会话：
  busy（有排队数，或状态字段不等于空闲值）：
      countdown 从起跑时刻算起：
          status = (countdown 已过 > 阈值 1800s) ? stuck : running
  idle：
      有新回复（更新时间 > 已读时间，或本轮运行 ≥20s）：
          每个新回复验一次最后一条消息（pageSize=1）：
              命中限流模板（见 5.3）→ stuck（红），meta 显示「限流」
              否则 → attention，且 countdown 从「刚转入待回复」那一刻重新起算 1800s
                  同一个待回复阶段内不重置；等满 1800s → stuck（等你回复太久）
      否则 → seen（prev 保留原状态，countdown 归零）
用户切到该标签页 / 单击该行且标签**确实切过去了** → acked_at=now, 已读时间=最新更新时间
      若当前不是 running → seen
      单击只是把命令交给「持有该标签的那个浏览器」，命令入队 / 排队中都不算读过；
      标签没切过去就不标已读，避免数字凭空消失。点击到落地之间又来了新回复，
      也不吃掉那次新回复（按点击那一刻的 updateTime 比）。
用户正停留在该会话标签页（窗口聚焦、上报 <120s）→ 回复直接记 seen，不计数、不弹提示
用户从该标签页切走 → **不要**补记已读。只有「切到某个标签」这一次上报算读，
      否则从看板点任务跳转时，被切走的那个会话会被误标已读、计数凭空消失。
      后台窗口（浏览器不在前台）里的切标签同样不算。
用户勾选 → done + muted（不再拉这个会话，直到取消勾选）
seen 且 48 小时内没有任何新进展（update_ms/acked_update 都不变）
      → 自动归档 archived=true，等同勾选，移出列表
      若归档后会话又有新 updateTime → 解除归档，回到 seen 暗色行
```

### 5.3 限流失败识别（不算交付，算卡住）

上游被限流时不会「失败」：它会正常停下，并写一条 assistant 消息，文案类似
「服务繁忙，本轮回答未能完成」。若只看状态字段，这会被误判成 attention（橙色），
用户以为有结果可读，实际要重试。

识别方式（低成本）：会话刚出现新回复时（`update_ms` 变化）请求
`GET /conversations/{cid}/messages?pageNo=1&pageSize=1`，取最后一条。
**结论不一次定死**：限流文案可能比消息本体晚落地，第一次翻没命中时，
在 5 分钟窗口内每隔 30 秒再翻一次（最多 4 次），期间标 attention；任一次命中即转 stuck。

```
命中条件（任一出现于 content，来自配置项 failure_marks，默认空表示不判定）：
  "服务繁忙"              # 部分平台在卡片标题里给这句
  "rate limit"           # 底层报错的常见写法
```

命中 → `status=stuck` + `failed=true`，计入红色卡住，行尾 meta 显示「限流」而不是计时。
不要用宽泛关键词（如单独的「限流」「稍后再试」）——正常回答里常见这类词，会误报。
`updateTime` 再变化时重新判定；`busy` 时（用户在重试）清掉 `failed`。

限流的性质（别搞错，会影响判断）：这是**模型调用侧的配额**（多数平台按 TPM，
即每分钟 token 数限流），报错通常是「请求被拒绝，请等待 N 秒后重试」这类文案。
它限制的是「你的账号在单位时间内能处理多少 token」，与打开网页、刷新页面、本工具的轮询**都无关**
（轮询只读会话列表和队列，不调用模型）。触发场景是：短时间内密集提问、单次上下文特别大、
或多个会话同时跑。知道这点才能给出正确建议——「别频繁刷新」没用，「等一会儿 / 拆小问题」才有用。

### 5.4 展示规则

- 列表默认只给 10 行（`window_limit`），排序：stuck > attention > running > seen > done。
- `seen` 行**只有对应标签页还开着**才展示（浏览器关掉即消失）。
  取不到标签快照超过 5 分钟时（浏览器没开/脚本失败）退化为全部展示，避免误清空。
- 分组默认折叠；含 stuck/attention 的组自动展开，只显示非 done 行。
- `archived`（48h 自动归档）的行不参与任何视图与计数。
- 计数口径：「进行中」= 此刻真的在跑（每轮由 busy 判定重算，与是否已读无关），
  所以点「进行中」只列真正的 running 行，保证数字与列表严格一致；
  已读的暗色行只在无筛选视图 /「全部」里出现（它表示「看过但已停下」，不是在干活）。
- 手动展开/折叠优先于自动展开。

### 5.5 「待确认」与「范围外」

两个标注都是「这个数字暂时不可全信」，含义不同，别混：

- **待确认**（行字段 `stale`，汇总在 `/state` 的 `stale_count`）：这一轮没拿到队列样本，
  显示的还是上次的状态。**只对运行中 / 待回复 / 已卡住三种会话提示**——它们本来就该在动，
  拿不到样本等于不知道该不该报。已查看 / 完成的会话不提示：它们安静是正常的，
  掉出监控窗口后没有样本也是正常的，不该一直挂着「待确认」。
- **范围外**（行字段 `covered=false`，汇总在 `/state` 的 `out_of_scope_count`）：
  会话超过 1 小时没再出现在会话列表里，状态只能当历史记录。行还留在列表里可查，
  但**不计入**「在跑 / 待回复 / 卡住」的实时汇总。`running` / `stuck` 的计数还额外要求
  不处于待确认，避免拿过期样本报数。

两条规则的取向一致：宁可承认「不知道」，也不用旧样本充数。

## 6. 架构（推荐实现方式，可按栈替换）

```
[浏览器扩展] --POST /tabs /active--> [本机后台服务 (HTTP :8899)] <--GET /state-- [悬浮窗 App]
                                    ^                                   |
                                    |--命令长轮询 /cmd-------------------+
[悬浮窗 App] --POST /open--> [后台服务] --命令入队--> [扩展] --chrome.tabs.update--> 浏览器
```

- **后台服务**：负责人形 Agent 的会话列表/队列拉取、状态机、状态落盘、对外 HTTP。
  **同一个常驻进程**里跑 HTTP + 取数线程（不要用「每分钟起一个新进程」的模式：
  每次启动要付 1.2~1.3s 的解释器/依赖加载，且每次都重建认证会话 → 频繁换 token，
  既慢又容易触发授权问题）。默认每 60 秒拉一份会话列表，按 `poll.watch_limit` 检查近期会话的队列。
  已经观测到的运行任务每 5 秒额外复查一批，每批最多 2 个，优先检查最久未采样的会话。
  每 5 秒还会单独拉一次列表（`poll.discovery_interval_seconds`），只为**新出现的会话**和
  **列表时间戳已跳变、状态还停在「已查看」的会话**（`poll.resume_probe_limit`，默认 1 个）取队列，
  让「新任务」和「老会话又起新一轮」都在 5 秒级进小窗，不必等下一个整分钟；
  这次列表复用了复查的节奏，不额外叠加。
  已经判定卡住的会话放慢到 `poll.stuck_interval_seconds`（默认 60 秒）复查一次，
  把 5 秒档留给真正在跑的——卡住的任务本来就不急，代价是它结束时晚 60 秒才发现。
  运行中超过 `poll.rate_limit_probe_seconds`（默认 60 秒）还没结束的会话，会翻一次最后一条消息，
  命中 `failure_marks` 就算「疑似被限流」直接转卡住并弹提示，不用等它转空闲；
  同一轮最多探 3 次、间隔翻倍，可以关掉（设为 0）。
  默认每个 60 秒周期最多追加约 25 次队列请求。空闲时只执行常规采样。
  `poll.active_interval_seconds`、`poll.discovery_interval_seconds` 和 `poll.active_watch_limit`
  可以调整，任一设为 0 即关闭对应的额外请求。
  首次运行以 `state.baseline_at` 为分界：这之前建的会话算历史，一次性记成「已查看」；
  之后新建的会话照常计入运行中，不会再被静默吞成已查看。
  请求串行执行，单轮预算 10 秒。队列采样失败会保留上次状态，运行中/待回复/卡住的会话
  标成「待确认」（口径见 5.5），安静的会话不标。
  认证做成可插拔的三种：`none`（不认证）、`token_file`（读一个 token 文件）、
  `module`（动态导入一个 Python 模块，适合有现成 SDK 的场景）。
  状态文件只存「标题/状态/时间/deadline」，**不存消息正文**，约 12KB。
- **两种取数来源**（`config.source`，面板上的 `API` / `WEB` 开关改的就是它）：`api` 由常驻进程
  用本机凭据直连接口；`web` 由扩展在目标站点页面里用**页面自己的 cookie** 取数再报给本机。
  运行时随时可切，不用重启。分组跟着来源走：`api` 用浏览器标签组，`web` 用平台侧分组。
  `web` 模式下扩展只选**一页**采集（优先用户正看着的那页），其余页面不开定时器；
  切到 `api` 立即收回采集权，采集页被关 / 被丢弃 / 重新加载时重新选主。
- **取数循环的两个坑**（都会让看板静默停摆，务必处理）：
  1. 有些认证 SDK 拿不到 token 时会直接 `sys.exit(1)`。在主线程表现为进程退出；
     在**子线程**里则线程静默消失、进程还活着、数字永远不动。取数线程外壳必须捕获
     `SystemExit` 和普通异常，记录原因并按指数退避重试（默认 60 秒起，每轮翻倍，上限 30 分钟）。
  2. 故障要写进状态（本实现 `state.poller_error` 并透传到 `/state`），
     否则用户只看到「数字不更新」，无从判断是没任务还是取数挂了。
- 凭据过期属于**外部依赖**：如果认证靠外部守护进程代换 token，产品里要提示
  「授权过期时按日志给出的地址完成一次绑定」，不要静默停摆。
- **悬浮窗 App**：纯原生（本实现是 Swift + AppKit，一个文件写完），只做渲染与输入，
  每 2 秒最多发起一次 `/state` 请求，连接失败时退避。网页看板每 3 秒读取一次，后台标签页暂停读取。
- **浏览器扩展**：只做两件事——上报标签页（URL/标题/分组名/tabId），以及**执行"切到某个标签页"的命令**。
  权限仅 `tabs / tabGroups / alarms` + 仅允许访问 `127.0.0.1`。

### 6.1 HTTP 契约（后台服务）

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/state` | 返回会话、计数、采样时间（`updated`）、待确认数（`stale_count`）、范围外计数（`out_of_scope_count`）、延迟分布（`latency`）和全局取数错误（`poller_error`） |

| GET | `/cmd?wait=1` | 扩展长轮询取命令（最长挂 10s，超时 204） |

### 6.2 跳转实现（性能是硬指标）

优先级从高到低：

1. **扩展长轮询通道**（目标 20~50ms）：`/open` 把 `{cmd:"focus", cid, url, tabId}` 放进队列，
   扩展挂着的长轮询立即取走 → `chrome.tabs.update(tabId,{active:true})` 与
   `chrome.windows.update(windowId,{focused:true})` **并行**发起。
2. 若没有扩展在等（扩展被系统回收），服务端**立即**走 AppleScript 兜底（约 150ms），
   **不要**先等一个固定超时再兜底（会导致偶发 0.5s 感知延迟）。
3. 兜底路径先查内存里的「会话 → 标签位置」映射，命中就一次 AppleScript 切过去；
   未命中才做一次全量枚举（这是最慢的分支，尽量少走）。

配套经验：
- 悬浮窗点击时**自己先把浏览器激活到前台**（`NSRunningApplication.activate`），
  不要等后台回包，否则「浏览器不在最前」时会额外多花 200ms+。
- 扩展每次切标签前用**缓存的 tabId** 单查（`tabs.get`），不要全量 `tabs.query`（100+ 标签时差一个量级）。
- 同一会话 1.5 秒内重复请求做去重，避免连点开出两个标签。
- 两个浏览器都装了扩展时，命令只发给**持有该标签的那一个**。发给另一个浏览器，
  它在那儿找不到标签就会新开一个——「不新开标签」这条硬要求就是这么破的。

### 6.3 「完成后提醒我」标记

右键任务行最上面一项。开着时：该行颜色提亮一倍并在左侧加一条竖条；这个会话
之后的回话弹窗铺 50% 状态色，且**不会自动消失**，必须手动点一下。

它只影响展示，不改状态判定、不影响卡住计时、不等于截止时间。开着标记的会话
即使没在跑也保持秒级复查，否则它掉出监控窗口后再有回话就取不到了。

对应接口 `POST /important?id=<cid>&value=1|0`，字段是 `/state` 里的 `important`。

### 6.4 批量清理标签页

右键菜单最下面一组（用分隔符隔开），四档同级，都只关**没在跑**的会话——
正在跑的把标签关掉，用户就看不到中间过程了：

| 项 | 关闭范围 |
|---|---|
| 关闭未工作的标签页 | 只要有标签、不在跑 |
| 关闭 1 小时未查看的 | 再加上「距最后更新超过 1 小时」 |
| 关闭 6 小时未查看的 | 同上，6 小时 |
| 关闭 24 小时未查看的 | 同上，24 小时 |

标题里带数量（如「关闭 24 小时未查看的（12）」），为 0 时该项置灰——这是
不可撤销的操作，先让人看清影响面。执行后标题栏回显「已关闭 N 个标签页」，3 秒消失。

接口 `POST /tabs/close?mode=idle|1h|6h|24h`。服务端按同一套规则**再筛一次**
（不信任端上算的结果），再交给扩展按 tabId 关；扩展关之前还会核对 URL 里的
`conversationId`，防止两次上报之间用户已经切走了。

**只关会话页**：标签 URL 必须在 `conversation_url` 的路径前缀下（本机是
`https://dataagent.corp.kuaishou.com/ai/data-agent`），且前缀后必须结束或紧跟
`?` / `#` / `/`。同域下的其它页面（登录页、`/ai/data-agent-history` 这类）
即使 URL 里恰好带 `conversationId` 也不会被当成会话标签——既不进标签映射，
也不会被批量关闭。前缀由 `install.command` 从配置生成，代码里不写死域名。

### 6.5 延迟指标

`/state` 的 `latency` 是**取数落定延迟**，不是跳转延迟：会话在上游列表里露出新状态
（`updateTime`）到本机把这轮状态算定（`attention` / `stuck` / `done`）。
单位毫秒，取最近 200 次，给 `samples`、`p50_ms`、`p95_ms`、`max_ms`；样本为 0 时只返回 `samples`。

只在状态**真的改变**时记一条样本，不是每次请求都记，所以它衡量的是「上游变了之后数字多久跟上」，
比看轮询间隔更接近用户感受。验收时用它代替「感觉有点慢」。

注意它不区分并行会话数：每轮复查的名额是共享的，同时跑的任务越多，同一条回复被发现得越晚
（合成回放里 1 / 5 / 10 / 15 个并行时，「结束到可见」P95 约 6.7 / 14.8 / 24.4 / 34.6 秒）。
所以「5 秒」是轮询节奏，不是端到端承诺；用户日常 5 个以内并行，按 15 秒档理解比较接近。

## 7. macOS 平台坑（本项目的血泪，务必避开）

1. **不要用系统窗口拖动**（`isMovableByWindowBackground = true`）。
   窗口拖动会话期间对窗口 `setFrame` 只改了逻辑 frame，屏幕上的位置和尺寸会被窗口服务器在会话收尾时回写——
   表现为「松手后过一会儿才收缩」「收缩后位置跳到屏幕中间」，而且你读回 `window.frame` 是"正确"的，无法自证。
   **正确做法**：自己实现拖动（`mouseDown` 记屏幕坐标 → `mouseDragged` 里 `setFrameOrigin` → `mouseUp` 立刻收尾）。
2. **贴边判定要用方向性比较**（`maxX >= screenRight - 26`），不能用 `abs(maxX - screenRight) <= 26`：
   用户经常把窗口拖得**越过**屏幕边缘，用绝对差反而判成"没贴边"，于是留在离边缘 170pt 的地方。
3. **多屏**：窗口移动时 `window.screen` 会切换到副屏（副屏在主屏左侧为负坐标），
   贴边计算若跟随 `window.screen` 会算错，应固定锚主屏 + 兜底 clamp。
4. **面板**：`NSPanel` + `.borderless` + `.nonactivatingPanel`，`collectionBehavior = [.canJoinAllSpaces, .fullScreenAuxiliary]`，
   `NSApp.setActivationPolicy(.accessory)`（无 Dock 图标）。
5. 自绘控件里 `NSTextField` 会拦掉鼠标事件：在容器视图 `hitTest` 里把 `NSTextField` 交回自己，否则细条上拖不动。
6. 收起/展开一律**保留窗口顶端**（top 边不动），纵向变化向下生长，避免"跳一下"的观感。

## 8. 验收用例（照着点一遍）

1. 收起态三枚胶囊显示 0/3/0，颜色正确；鼠标移入 0.1s 内展开，移出 0.15s 后收起。
2. 拖到右边缘松手：**同一帧**收成 44pt，停在松手高度，且右边紧贴屏幕（不留缝）。
3. 从屏幕另一侧快速拖到边缘：不出现"停顿后再收缩"。
4. 拖到屏幕中间松手：不收缩（或按产品选择保持展开），位置不跳。
5. 单击任务行：编辑器…浏览器切到该会话的**已存在**标签；再点一次仍在同一标签（不新开）。
6. 关闭浏览器，等 5 分钟：App 不崩、状态不清空；重新打开浏览器后标签关联恢复。
7. 点计数胶囊（含 0 值）：列表切换为对应类别，已查看行暗色，计数不变。
8. 勾选任务：行立即消失，且该会话不再触发提醒；取消勾选（在"显示全部"里）后恢复监控。
9. Agent 回话：右上角弹提示条，15 秒消失；连来 3 条时向下堆叠且每条的标题/任务名都可见；点任意一条 ≤60ms 切到标签。
10. 重启 App：位置、展开/收起、图钉状态与上次一致。

## 10. 跨平台评估（Windows）

不建议做，成本与收益不成比例。原因：

- UI 层是 AppKit 专有实现（悬浮面板、毛玻璃、非激活窗口、屏幕边缘坐标换算），Windows 需换 WinUI/Electron 重写全部交互；
  尤其"不抢焦点 + 置顶 + 多显示器"这套在 Win32 上是另一套 API（TopMost + WS_EX_NOACTIVATE）。
- 后台服务的 AppleScript 链路在 Windows 上不存在，只能用扩展通道（这部分代码可以复用）。
- 自启动、日志、安装包（launchd → 任务计划程序）都要重写。
- 若要跨平台，建议**直接选一个跨平台壳**（Tauri/Electron）重做 UI，并保留同一套 HTTP 契约与扩展，而不是移植现有代码。
  工作量估计：跨平台重写 ≈ 现有 macOS 版本的 1.5~2 倍。
